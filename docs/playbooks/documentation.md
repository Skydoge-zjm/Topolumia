# 文档维护与任务交接

入口是根 [AGENTS.md](../../AGENTS.md)，按任务导航在 [docs/README](../README.md)。Claude Code 的根 CLAUDE.md 只导入共同入口；支持 AGENTS.md 的工具直接使用它，不再维护平行项目知识。

## 应更新哪里

| 变化 | 归属 |
| --- | --- |
| 领域概念、关系或业务规则 | product/business |
| 用户操作、结果与验收 | product/requirements，与业务并列 |
| 跨模块责任、权威数据与授权 | technical/architecture |
| 局部机制、特殊约束与代码入口 | technical/modules，先一份 README |
| 需要长期解释的重要取舍 | technical/decisions，简短说明原因与后果 |
| 重复执行的方法 | playbooks，引用规则而不复述 |
| 特定任务的未定方案、计划与进度 | work/active，仅复杂任务需要 |

一个定义只有一个归属。能从类型、Schema、帮助或代码直接获取的完整字段/文件清单不重复编写。模块需要真实代码入口和适当验证链接，不强制所有模块相同篇幅或多份文件。

## 常驻入口的选材

AGENTS.md 只放跨任务的开发约定、必要命令、难以从代码推断的工程提醒与按需导航。业务规则、功能行为和模块实现约束放在各自文档，不因为重要或曾多次出错就提升为每个任务都要加载的指令。

例如科研写入、Trace 保留、任务限时和环境梗概分别归属对应业务或技术主题；界面样式归属前端设计。常驻入口不重复这些内容，也不另建一份要求默认读取的“重要约束大全”。

维护时逐条判断是否对无关任务也有帮助。行数预算仅防止膨胀，不能证明选材合理；删掉过时或可推导的说明，比压缩句子更重要。

## 状态与内容

业务/需求是有效产品结论；“已确定”不等于“已实现”。需求写明实现差距；技术默认描述当前实现，目标设计明确标注。元数据不是必填模板，只有确有检索需求时再加。

正文记录机制、约束与原因，不按日期叠加修补段落。重要规则尽量连接到类型、校验、lint 或有意义测试；没有可执行验证时如实说明，不为了凑链接创建空测试。

## 长任务

work/active/<task>/plan.md 通常只需：目标与验收、必要背景链接、已完成、下一步、阻塞与未决事项、验证范围和结果。复杂取舍才新增 proposal.md。

发生阶段性变化、阻塞或交接前更新，不能变成逐条工具日志。新会话应能独立恢复工作，但不需要把聊天全文或原始输出复制进去。

完成后先把有效产品/技术结论写回主文档，再将仍有交接价值的工作项移到 completed；没有价值的任务记录可直接删除。截图、日志与重复审阅稿不随完成目录保存。历史任务不进入默认知识读取链。

## 链接与验证

内部链接使用相对 Markdown 链接，路径与锚点应存在；示例命令放代码块。不要在正式文档引用 runtime 临时截图作为长期证据。第三方 references 单独保留，不作为自有合同。

从源码根执行：

```powershell
npm run docs:check
```

检查正式文档的本地链接、锚点、导航可达性、共同入口引用和入口预算，并拒绝对本机任务记录或参考资料的链接。检查不要求 docs/work 或 docs/references 存在，也不读取其中的内容。静态检查不能证明文档与代码语义一致，改动时仍需核对真实实现。

## 与代码共同维护

正式产品、技术和操作文档随源码在同一 Git 仓库维护。修改功能或架构时，同步修改对应文档并在同一次提交中记录；追溯使用普通 Git 历史，不在正文叠加变更经过。

从源码根查看代码与文档的全部差异：

```powershell
git status --short
```

docs/work 和 docs/references 由根 .gitignore 排除，保留本机。任务结论如需成为长期知识，应整理进正式文档；不要强制添加整个任务目录或下载的参考项目。

公开文档中的链接必须在普通克隆和源码导出中可用；本机目录名称可用普通文字说明，但不能成为正式文档的读取依赖。

源码导出由 [导出器](../../scripts/release/export-source.mjs) 筛选正式文档并排除本机材料。调整公开范围时同步修改 Git 忽略规则、导出规则和必要测试，不能只改其中一处。
